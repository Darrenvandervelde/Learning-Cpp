# Module Authoring and Academic Quality Standard

## 1. Purpose

Every numbered module must be a teachable, assessable unit. A short topic summary is not a complete module. The lesson must provide enough explanation and practice for a learner to reach the stated outcomes without relying on undocumented assumptions.

## 2. Required module specification

Every module README must state:

1. Module number and title.
2. Expected study time as a planning estimate, not academic credit.
3. Prerequisite modules and prerequisite knowledge.
4. A concise module description.
5. Measurable learning outcomes using observable verbs.
6. Required terminology.
7. Topic sequence.
8. Required tools and environment.
9. Assessment evidence and pass requirements.
10. References and further reading.

## 3. Required teaching content

The theory area must explain each major concept through:

1. Definition and purpose.
2. Mechanism and relevant language rules.
3. A small annotated C++20 example.
4. Expected compiler or runtime behaviour.
5. Memory, lifetime, ownership and performance implications where relevant.
6. Common incorrect approaches and why they fail.
7. A game development application.
8. Comparison of alternatives and their trade offs.
9. Questions that test conceptual understanding.

Do not introduce a feature without explaining its preconditions, guarantees and limitations.

## 4. Required laboratory design

Each laboratory must contain:

1. A clear objective.
2. Required starting files and environment.
3. A sequence of manageable tasks.
4. A prediction question before execution.
5. A build or execution procedure.
6. Expected observations without giving away every solution.
7. A troubleshooting section.
8. A submission checklist.

Students should record compiler versions, build commands, test input and observed output. Documentation must distinguish expected results from results that have actually been verified.

## 5. Required independent exercises

Exercises must progress from focused practice to transfer:

1. Explain or predict a small code fragment.
2. Identify and diagnose a defect.
3. Modify an existing example with a stated requirement.
4. Implement a new feature independently.
5. Explain design choices and limitations.

At least one exercise must use a game development context.

## 6. Required assessment design

The assessment area must contain:

1. Technical questions.
2. Code reading and defect analysis.
3. An independent implementation task.
4. Engineering reasoning questions.
5. The marking rubric and mandatory pass conditions.

Do not publish the complete solution to an active assessment before the student attempts it. Reassessments must use new questions or a materially different implementation task.

## 7. Required project design

The project area must define the problem, functional requirements, constraints, input and output behaviour, edge cases, build procedure, expected evidence and acceptance criteria. Projects should integrate earlier knowledge without silently requiring concepts that have not yet been taught.

## 8. Writing and formatting rules

Use clear academic English and define specialist terminology. Prefer descriptive headings, numbered procedures and tables. Avoid decorative punctuation in prose. Use standard hyphen characters only where technically necessary, including filenames, command line options, identifiers and URLs. Do not alter a compiler flag or file path merely to remove punctuation.

## 9. References

Prefer primary sources and authoritative documentation. Identify the author or organization, title and URL. Distinguish normative language references from explanatory tutorials. Do not fabricate citations, page numbers or publication details.

## 10. Review checklist

A module is ready for learner use only when:

1. Its outcomes are measurable.
2. Prerequisites are explicit.
3. Theory explains mechanisms and limitations.
4. Examples are complete and build instructions are reproducible.
5. Exercises require independent reasoning.
6. Assessment aligns with the outcomes.
7. The rubric and progression gate are explicit.
8. References are relevant and verifiable.
9. No unverified execution claim is made.
10. The module contributes to the cumulative game project.
